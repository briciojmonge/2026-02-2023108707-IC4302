## Respuestas

### HA

El concepto de HA hace referencia a la High Availabillity de una base de datos. Es una métrica que se usa para medir cuantitativamente la resilencia de lsa bases, y se mide como el porcentaje del tiempo que esta disponible para su uso.

La lectura menciona que una base de datos con alta disponibilidad debe de poder ser operacional en eventos como fallos en hardware, software o de redes sin o con poca interaccion manual.

### DR

Se desarrolla en inglés como Disaster recovery, y como recuperación de desastres en español, son metodos en los que las organizaciones pueden volver a tener acceso y funcionalidad de su infraestrucrura despues de un desastre humano o natural. Las politicas para la recuperación ante los desastres pueden requerir de interaccion manual corriendo scripts o cambiando configuraciones.

Estos procedimientos cuentan con estrategias de "backups" robustas, y permiten que en caso de un desastre natural donde se pierda un cnetro de datos en una región, se pueda replicar en otro centro de datos de una región que no haya sido afectada.

### RPO

RPO se refiere a la cantidad máxima de tiempo que es permitible que transcurra desde que se guardo el ultimo "recovery point". Define cuantos datos se pueden perder entre puntos de recuperación. Si se definen 20 minutos de RPO en caso de una interrupción se pueden perder 20 minutos de datos.

### RTO

Por otro lado RTO se refiere a el delay maximo aceptable entre la interrupción de la base de datos y la recuperación del servicio. Define lo que se considera una ventana de tiempo aceptable cuando la base de datos no esta disponible. Un RTO de 5 minutos significa que la base de datos debe volver a ser funcional en como mucho 5 minutos.

### Arquitectura de AuroraDB

Amazon Aurora es una base de datos relacional administrada, compatible con MySQL y PostgreSQL.  Aurora combina almacenamiento distribuido, failover automático, backups gestionados y replicación global para ofrecer HA y DR tanto en una región como entre múltiples regiones, permitiendo aplicaciones globalmente resilientes con RTO y RPO ajustables según el negocio. Su arquitectura está diseñada para alta disponibilidad y resiliencia:

- Almacenamiento distribuido: Aurora replica cada escritura seis veces en tres zonas de disponibilidad. Tolera la falla completa de una AZ más la falla concurrente de un nodo de almacenamiento en otra AZ (AZ+1). El almacenamiento escala y se auto-repara usando protocolos peer-to-peer.

- Separación de cómputo y almacenamiento: El clúster tiene un escritor y hasta 15 lectores. Los lectores sirven lecturas y pueden ser objetivos de failover. Se usan endpoints: el endpoint de clúster apunta siempre al escritor actual; el endpoint de lector balancea entre lectores.

- Multi-AZ: Configuración HA de una sola región. Aurora detecta fallos del escritor y promueve automáticamente un lector según prioridad (0 a 15). El failover puede tardar hasta 60 segundos y el servicio de RDS Proxy puede reducirlo hasta en un 66 %, el AWS JDBC Driver ayuda a reconectar rápidamente.

- Backups: Aurora ofrece backups automáticos continuos con retención de 1 a 35 días, PITR y snapshots manuales que no expiran. AWS Backup permite gestionar copias y retención centralizada.

- Aurora Global Database: Permite extender un clúster a varias regiones. Replica asíncronamente con latencia típica menor a 1 segundo. Soporta hasta 5 regiones secundarias y hasta 90 lectores en total. Si la región primaria falla, se puede promover una secundaria. Ofrece Switchover (sin pérdida de datos, RPO=0, para mantenimiento o rotación) y Failover (para desastres, puede haber pérdida de datos no replicados). También permite configuraciones headless en secundarias para reducir costos, write forwarding para escrituras locales desde secundarias, y monitoreo con métricas como AuroraGlobalDBRPOLag.

- Mantenimiento y cambios disruptivos: Blue/Green Deployments permiten probar y promover entornos verdes con mínimo downtime. Zero-Downtime Patching (ZDP) reduce el impacto de parches menores.

- Monitoreo: CloudWatch, Enhanced Monitoring y Performance Insights permiten observar métricas como AuroraReplicaLag, CPUUtilization, AuroraGlobalDBReplicationLag, entre otras.
